    What Tau is

    • The Tau Language is a formal specification language that IDNI describes as expressive, decidable and executable: a specification can be checked for satisfiability, and the framework can synthesize a program that meets it. IDNI calls it work in progress, with releases in an alpha state.

      Source: tau-lang README, introduction

    • Tau Testnet Alpha is a live blockchain whose consensus rules are a Tau program. A Python host does networking, storage and cryptography; the Tau program decides block validity, who may propose a block, transfers and fees.

      Source: tau-testnet README, top Consensus boundary

    The testnet chain

    • Blocks come from an on-chain proof-of-authority validator set, not from mining by proof of work or from staking. Only validators in the active set may propose blocks, and the set changes only through on-chain governance.

      Source: tau-testnet README, features Node roles

    • Fork choice is the highest chain, ties broken by the smallest block hash. There are no checkpoints, so a reorganisation can go back as far as the common ancestor (a switch longer than 2000 blocks is refused).

      Source: Security & risk model

    • The public network is called tau-testnet-v2. Everything needed to join it (genesis, bootnode address, network id) is committed in IDNI's repository; every node must have the same genesis hash and network id or the other nodes refuse it.

      Source: Join the Tau Testnet networks/tau-testnet-v2

    • The tau-testnet-v2 genesis file funds 11 accounts: one with 1,000,000 and ten with 100,000. It names one active validator and the supermajority voting rule. How many validators are active today: see the live numbers.

      Source: genesis.json

    Accounts, payments, fees

    • The tau-testnet-v2 join profile switches on an automatic faucet: a new account receives 100,000 test tokens on its first transaction. (A network made with IDNI's genesis script has no faucet unless it is set.)

      Source: networks/tau-testnet-v2/env Operating a network

    • Accounts are BLS12-381 keys. An address is the public key: 96 lowercase hex characters (48 bytes), without 0x. A private key is 64 hex characters (32 bytes); signatures are 96 bytes.

      Source: Cryptography & signatures Operating a network

    • A transfer is three values: from, to, amount; one transaction can carry several. There is no memo or message field. One transfer can move at most 16,777,215 (amounts are 24-bit numbers).

      Source: Transaction signing fields Amount cap

    • The base fee comes from the consensus rules themselves (the genesis rule sets 10 per transfer step) and validators can vote to change it. Only ordinary user transactions pay; the fee goes to the block's proposer, unless governance names a fixed receiver. The fee a transaction states is a limit: the sender pays the actual fee, not the limit.

      Source: Transaction fees

    • Each account's transactions carry a sequence number; a gap is refused. There is no replace-by-fee: a stuck transaction has to expire or be evicted.

      Source: Mempool policy

    • A retractable transfer waits in escrow until a set block height or time; until then only the sender can take it back, without a fee. At most 16 can be open per sender (4096 on the whole chain), and the release can be at most 100,000 blocks or 90 days ahead.

      Source: Retractable transfers docs/retractable.md

    Rules people give their own accounts

    • A user can give their own account a Tau rule that blocks some of their own transfers, for example only to listed recipients or nothing above an amount. The chain enforces it when the transaction is admitted and again when the block is applied. A rule binds only the account that set it.

      Source: Consensus boundary, o5

    • In the current code at most 2 accounts can hold a registered personal transfer rule at the same time, chain-wide; IDNI notes that raising the number needs new measurements.

      Source: consensus/approvals.py

    • One user can offer a Tau rule to another, who checks it and accepts or rejects it. Offer, accept and reject are transactions and pay fees. An accepted rule cannot be withdrawn, only replaced by accepting another rule for the same output.

      Source: Rule sharing Caveats

    • A user can require a co-signature for their own large transfers: their rule names an amount and an approver. A transfer above it waits on the chain and goes through by itself once the approver's signed vote arrives.

      Source: docs/approvals.md

    Changing the chain's own rules

    • The chain's own consensus rules and its validator set change only through governance on the chain: a proposal carries the full new rules, validators vote, and with the supermajority rule it needs at least two thirds of the active validators.

      Source: Governance

    • An agreed change takes effect only at a later block height (at least as many blocks ahead as there are validators). A proposal that has not reached its votes when that height arrives expires. A change that fails to compile is refused.

      Source: Governance lifecycle consensus/engine.py

    Running a node

    • A node uses three ports: 65432 (RPC and command line), 65433 (WebSocket, used by the web wallet) and 4001 (peer-to-peer). Only 4001 is meant to be public: RPC and WebSocket have no authentication.

      Source: Quickstart RPC / WebSocket exposure

    • The quickest way to run a node is IDNI's standalone Docker image, which builds the Tau engine inside it. Linux and macOS also run it from source (Python 3.14 or newer); Windows needs Docker Desktop or WSL2. Anyone can run a read node; proposing blocks needs a seat in the validator set.

      Source: Quickstart Windows Run from source Node roles

    • IDNI's repository includes a browser wallet (web-wallet/) that talks to a node's WebSocket port and keeps private keys in the browser. It is not served by the node; it is opened with a static web server.

      Source: Web wallet

    What the testnet does not promise

    • The testnet is alpha: its tokens have no real value, there is no finality, no validator slashing, the cryptography and consensus are not audited, and IDNI warns not to use it with real funds.

      Source: tau-testnet README, status

    • Signatures do not yet include the network id, so a signed transaction is not tied to one network. IDNI's advice: do not reuse keys across networks.

      Source: Cryptography & signatures

    • IDNI lists known alpha risks: deep reorganisations are possible, a crash in the Tau engine can stop a node process, and a bad governance change can halt the chain until it is corrected.

      Source: Status
